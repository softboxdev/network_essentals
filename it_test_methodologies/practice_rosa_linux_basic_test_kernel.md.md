# Практическая работа: Тестирование информационной системы в Linux (Bash)

**Тема:** Простейшее тестирование информационной системы с помощью bash-скриптов.

**Цель работы:** Научиться писать bash-скрипты для автоматической проверки работоспособности информационной системы: доступность сервисов, корректность ответов, целостность данных и логирование результатов.

**Оборудование и ПО:** ПК с ОС Linux (РОСА Линукс, Ubuntu, Fedora), терминал, установленный `curl`.

---

## Теоретическая справка

**Тестирование информационной системы (ИС)** — это проверка того, что система работает согласно требованиям: сервисы доступны, отвечают корректно, данные не повреждены, ошибок в логах нет.

Виды простейших проверок в bash:

| Тип проверки | Инструмент | Что проверяем |
|---|---|---|
| Доступность порта | `nc`, `curl`, `/dev/tcp` | Сервис слушает порт |
| HTTP-ответ | `curl -s -o /dev/null -w "%{http_code}"` | Код ответа 200/301/404 |
| Содержимое ответа | `curl` + `grep` | Наличие ключевого текста |
| Файлы и права | `test`, `ls`, `stat` | Наличие, права, размер |
| Процессы | `pgrep`, `ps` | Сервис запущен |
| Целостность данных | `md5sum`, `diff` | Файл не изменён |

**Коды возврата (exit codes)** — основа тестирования:
- `0` — тест пройден (успех);
- `1` — тест провален (ошибка);
- другие коды — специфические ошибки.

## Ход работы

### Шаг 1. Подготовка рабочей папки и тестовой «системы»

Создадим директорию для тестов и сымитируем простую информационную систему: файл данных и веб-сервер на Python.

```bash
mkdir -p ~/qa_test/{logs,data}
cd ~/qa_test

# Создаём "данные" ИС
echo "id,name,status" > data/users.csv
echo "1,Ivan,active" >> data/users.csv
echo "2,Petr,blocked" >> data/users.csv

# Запускаем простой HTTP-сервер на порту 8080 в фоне
python3 -m http.server 8080 --directory ~/qa_test/data &
echo $! > /tmp/qa_http.pid
```

Проверьте, что сервер отвечает:

```bash
curl -s http://localhost:8080/users.csv
```

### Шаг 2. Создание скрипта тестирования

Создайте файл `run_tests.sh`:

```bash
nano run_tests.sh
```

Введите код:

```bash
#!/bin/bash
# ============================================================
# Скрипт автоматического тестирования информационной системы.
# Проверяет доступность HTTP-сервера, корректность ответов,
# целостность файлов данных и наличие процессов.
# Возвращает 0, если все тесты пройдены, иначе 1.
# ============================================================

# ---------- Глобальные переменные ----------
# Объявлены ДО функции check(), поэтому видны внутри неё
# и сохраняют изменения после выхода из функции.
PASS=0   # счётчик пройденных тестов
FAIL=0   # счётчик проваленных тестов

LOG_FILE="$HOME/qa_test/logs/test_$(date +%Y-%m-%d_%H-%M-%S).log"
# Путь к файлу лога. $(date ...) подставляет текущую дату и время,
# чтобы каждый запуск писался в отдельный файл и не перезатирал старый.
# Формат: test_2024-09-16_14-22-01.log

HOST="localhost"   # хост тестируемой системы
PORT="8080"        # порт, на котором слушает HTTP-сервер
URL="http://$HOST:$PORT/users.csv"
# Итоговый URL. Переменные раскрываются при подстановке:
# получится "http://localhost:8080/users.csv"

# ---------- Функция логирования ----------
log() {
    echo "[$(date '+%H:%M:%S')] $1" | tee -a "$LOG_FILE"
    # echo формирует строку: "[14:22:01] текст сообщения"
    #   $(date '+%H:%M:%S') — текущее время в формате ЧЧ:ММ:СС
    #   $1 — первый аргумент функции log (текст сообщения)
    # | tee -a "$LOG_FILE" — вывод идёт ОДНОВРЕМЕННО:
    #   • в консоль (чтобы видеть прогресс),
    #   • в файл лога в режиме добавления (-a = append).
    # Без -a файл перезаписывался бы при каждом вызове.
}

# ---------- Функция проверки ----------
# $1 — название теста (для человека)
# $2, $3, ... — команда, которую надо выполнить (должна вернуть 0)
check() {
    local name="$1"
    # local — переменная существует только внутри check().
    # Без local она стала бы глобальной и могла затереть чужую name.
    # name="$1" — сохраняем название теста (первый аргумент).

    shift
    # Сдвигаем позиционные параметры влево: $2 → $1, $3 → $2 и т.д.
    # Старый $1 (название теста) отбрасывается.
    # После shift в "$@" остаётся только команда для выполнения.

    if "$@" >/dev/null 2>&1; then
        # "$@" — все оставшиеся аргументы как ОТДЕЛЬНЫЕ слова.
        #   Кавычки обязательны: сохраняют пробелы внутри аргументов.
        #   Если написать $@ без кавычек — аргументы разобьются по пробелам.
        #   Если написать "$*" — всё склеится в одну строку. Оба варианта сломают команду.
        #
        # >/dev/null — stdout (дескриптор 1) уходит в «чёрную дыру».
        #   Нам не нужен вывод curl/теста в консоли.
        # 2>&1 — stderr (дескриптор 2) перенаправляется туда же, где stdout.
        #   Ошибки команды тоже глушим.
        #   Порядок важен: сначала >/dev/null, потом 2>&1.
        #
        # if проверяет КОД ВОЗВРАТА команды:
        #   0  → истина → ветка then (тест пройден),
        #   ≠0 → ложь  → ветка else (тест провален).

        log "PASS: $name"
        # Пишем в лог и консоль строку об успехе.

        PASS=$((PASS + 1))
        # $(( ... )) — арифметическое расширение.
        # Увеличиваем глобальный счётчик PASS на 1.
        # PASS объявлена БЕЗ local, поэтому изменение сохраняется.
    else
        log "FAIL: $name"
        # Тест провален — пишем FAIL.

        FAIL=$((FAIL + 1))
        # Увеличиваем счётчик провалов.
    fi
    # fi — закрывает блок if/else. Обязателен в bash.
}

# ---------- Начало выполнения ----------

log "===== Старт тестирования ИС ====="
# Первая запись в лог — отметка о запуске скрипта.

# ТЕСТ 1. Проверяем, что HTTP-сервер вообще отвечает на запрос.
check "HTTP-сервер доступен на порту $PORT" \
    bash -c "curl -s -o /dev/null --max-time 3 $URL"
    # \ в конце строки — перенос длинной команды на следующую строку.
    #   Bash воспринимает это как одну команду.
    # bash -c "..." — запускаем вложенный bash с командой в кавычках.
    #   Нужно, потому что check() сам вызывает "$@", а нам надо
    #   выполнить целую конструкцию с перенаправлениями и пайпами.
    # curl -s — «тихий» режим, без прогресс-бара.
    #   -o /dev/null — вывод curl выбрасываем.
    #   --max-time 3 — таймаут 3 секунды; если сервер не ответит, curl вернёт ошибку.
    #   Если curl завершится с кодом 0 → сервер доступен → PASS.

# ТЕСТ 2. Проверяем, что HTTP-код ответа именно 200 (а не 404, 500 и т.д.).
check "HTTP-код ответа = 200" \
    bash -c "[ \"\$(curl -s -o /dev/null -w '%{http_code}' $URL)\" = '200' ]"
    # Внутри bash -c используется конструкция [ ... ] — это команда test.
    #   Она возвращает 0, если выражение истинно, и 1, если ложно.
    # \$(curl ...) — экранированный $, чтобы подстановка произошла
    #   ВНУТРИ bash -c, а не снаружи, во внешнем скрипте.
    #   Без \ внешний bash попытался бы выполнить curl сам и подставить
    #   результат до запуска bash -c — это тоже сработало бы, но логика
    #   была бы другой.
    # -w '%{http_code}' — curl печатает только HTTP-код (200, 404, 500).
    # Сравниваем полученный код со строкой '200'.
    #   Кавычки вокруг $(...) обязательны: код может быть пустым,
    #   и без кавычек [ = '200' ] вызвал бы синтаксическую ошибку.

# ТЕСТ 3. Проверяем, что ответ содержит ожидаемый заголовок CSV.
check "Ответ содержит заголовок 'id,name,status'" \
    bash -c "curl -s $URL | grep -q 'id,name,status'"
    # curl -s $URL — получаем содержимое файла.
    # | — пайп: stdout curl идёт на stdin grep.
    # grep -q — «тихий» режим: ничего не печатает, только возвращает код.
    #   Нашёл совпадение → 0 (PASS).
    #   Не нашёл → 1 (FAIL).

# ТЕСТ 4. Проверяем, что файл данных существует и не пустой.
check "Файл users.csv существует и не пуст" \
    test -s "$HOME/qa_test/data/users.csv"
    # test -s FILE — истинно, если FILE существует И его размер > 0.
    #   Если файла нет или он пуст → код возврата 1 → FAIL.
    # Здесь не нужен bash -c: test — самостоятельная команда,
    #   check() вызовет её напрямую через "$@".

# ТЕСТ 5. Проверяем количество строк в файле.
check "Файл users.csv содержит 3 строки" \
    bash -c "[ \"\$(wc -l < $HOME/qa_test/data/users.csv)\" -eq 3 ]"
    # wc -l — считает строки.
    #   < FILE — перенаправление ввода: wc читает из файла, а не со stdin.
    #   Если написать wc -l FILE, вывод будет "3 FILE" — сравнение сломается.
    #   С < FILE вывод — только число.
    # -eq 3 — числовое сравнение «равно 3».
    #   Для чисел используется -eq/-ne/-lt/-gt, для строк — = / != .

# ТЕСТ 6. Проверяем, что процесс http.server запущен.
check "Процесс python3 http.server запущен" \
    pgrep -f "http.server 8080"
    # pgrep ищет процессы по имени.
    #   -f — искать по полной командной строке, а не только по имени.
    #   Без -f pgrep искал бы процесс с именем "http.server 8080",
    #   которого не существует (имя процесса — python3).
    #   Нашёл хотя бы один → 0 (PASS), не нашёл → 1 (FAIL).

# ТЕСТ 7. Проверяем, что порт слушается (низкоуровневая проверка).
check "Порт $PORT слушается" \
    bash -c "timeout 2 bash -c '</dev/tcp/$HOST/$PORT'"
    # /dev/tcp/HOST/PORT — специальный виртуальный файл в bash.
    #   Открытие его на чтение = попытка TCP-подключения.
    #   Если порт открыт — bash успешно открывает файл, код 0.
    #   Если закрыт — ошибка подключения, код ≠ 0.
    # timeout 2 — ограничиваем попытку 2 секундами.
    #   Без timeout при «висящем» порте скрипт завис бы навсегда.
    # Вложенный bash -c нужен, потому что /dev/tcp работает только
    #   в интерактивном bash или в bash -c; в sh его нет.

# ТЕСТ 8. Проверяем права на чтение файла.
check "Файл users.csv доступен для чтения" \
    test -r "$HOME/qa_test/data/users.csv"
    # test -r FILE — истинно, если файл существует и доступен на чтение
    #   текущему пользователю.
    # Это проверка прав доступа, а не содержимого.

# ТЕСТ 9. Проверяем наличие конкретной записи в данных через HTTP.
check "В данных есть запись 'Ivan'" \
    bash -c "curl -s $URL | grep -q 'Ivan'"
    # Берём данные по HTTP (а не из файла) — проверяем,
    #   что сервер отдаёт актуальное содержимое.
    # grep -q ищет подстроку 'Ivan' в ответе.

# ТЕСТ 10. Проверяем отсутствие слова "error" в ответе.
check "Ответ не содержит слова 'error'" \
    bash -c "! curl -s $URL | grep -qi 'error'"
    # ! — логическое отрицание кода возврата следующей команды.
    #   Если grep нашёл 'error' (код 0), то ! превращает 0 в 1 → FAIL.
    #   Если grep не нашёл (код 1), то ! превращает 1 в 0 → PASS.
    #   Логика инвертирована: нам нужно, чтобы ошибок НЕ было.
    # grep -qi — q (тихо) + i (игнорировать регистр: error, Error, ERROR).

# ---------- Итог ----------

log "===== Результаты ====="
log "Пройдено: $PASS"
log "Провалено: $FAIL"
log "Лог сохранён: $LOG_FILE"
# Печатаем сводку. Переменные раскрываются в значения счётчиков
# и путь к логу, сохранённый в начале скрипта.

if [ "$FAIL" -eq 0 ]; then
    # [ ... ] — команда test.
    # "$FAIL" -eq 0 — истинно, если счётчик провалов равен нулю.
    # Кавычки вокруг $FAIL не обязательны для чисел, но безопасны.
    log "ИТОГ: Все тесты пройдены успешно!"
    exit 0
    # exit 0 — завершаем скрипт с кодом успеха.
    #   Это важно: если скрипт запускается из cron или CI,
    #   код возврата определяет, считать ли запуск успешным.
else
    log "ИТОГ: Есть проваленные тесты!"
    exit 1
    # exit 1 — завершаем с кодом ошибки.
fi
```

# Где и как запускать скрипт тестирования — подробно

Разберём все способы запуска: от ручного в терминале до автоматического по расписанию. Для каждого — где, зачем и как.

---

## 📍 Способ 1. Запуск вручную из терминала

**Где:** локальный терминал на том же ПК, где установлена тестируемая ИС.

**Когда использовать:** при отладке скрипта, разовых проверках, обучении.

### 1.1. Открыть терминал

- В РОСА Линукс: меню «Пуск» → «Терминал», или горячие клавиши `Ctrl+Alt+T`.
- Либо через `Ctrl+Alt+F2` (виртуальная консоль), но там нет графики — для тестов неудобно.

### 1.2. Перейти в директорию со скриптом

```bash
cd ~/qa_test
```

### 1.3. Проверить права на выполнение

```bash
ls -l run_tests.sh
```

Должно быть `-rwxr-xr-x`. Если нет `x` — добавьте:

```bash
chmod +x run_tests.sh
```

### 1.4. Запустить скрипт

Три равнозначных варианта:

```bash
./run_tests.sh          # как исполняемый файл (нужен chmod +x)
bash run_tests.sh       # явно указать интерпретатор (chmod не нужен)
source run_tests.sh     # выполнить в текущей оболочке (см. предупреждение ниже)
```

> ⚠️ **Про `source`:** выполняется в **текущей** оболочке, а не в дочерней. Все переменные (`PASS`, `FAIL`, `LOG_FILE`) останутся в вашем терминале после завершения, а `exit 0` **закроет ваш терминал**. Для тестов используйте `./` или `bash`.

### 1.5. Проверить код возврата

```bash
./run_tests.sh
echo "Код возврата: $?"
```

- `0` — все тесты прошли.
- `1` — есть провалы.

Этот код важен для интеграции с cron и CI.

### 1.6. Посмотреть лог

```bash
ls -lt ~/qa_test/logs/          # список логов, свежие сверху
cat ~/qa_test/logs/test_*.log   # содержимое последнего
tail -f ~/qa_test/logs/test_*.log  # следить в реальном времени
```

## 📍 Запуск из другой директории (по абсолютному пути)

**Где:** из любого места файловой системы.

**Когда использовать:** скрипт лежит в пути, например в `/opt/scripts/`, а вы работаете из домашней папки `~`.

```bash
/opt/scripts/run_tests.sh
```

Или через `bash`:

```bash
bash /opt/scripts/run_tests.sh
```

> ⚠️ **Важно:** внутри скрипта все пути должны быть **абсолютными** , например в (`$HOME/qa_test/...`) или вычисляться от расположения скрипта. Если использовать относительные пути (`./data/users.csv`), при запуске из другой директории они сломаются.

Пример правильного определения директории скрипта в начале:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
LOG_FILE="$SCRIPT_DIR/logs/test_$(date +%Y-%m-%d_%H-%M-%S).log"
```

## 📍 Запуск из другого скрипта

**Где:** внутри более крупного скрипта (например, общего health-check всей системы).

**Когда использовать:** тесты ИС — часть большой проверки.

```bash
#!/bin/bash
# main_check.sh

echo "=== Проверка всей системы ==="

# Вызов тестов ИС с проверкой кода возврата
if /home/user/qa_test/run_tests.sh; then
    echo "ИС: OK"
else
    echo "ИС: ПРОБЛЕМЫ" >&2
    # Можно отправить алерт
fi
```

## 📍  Отладка: запуск с трассировкой

**Где:** терминал, при поиске ошибок в скрипте.

**Когда использовать:** скрипт ведёт себя не так, как ожидалось.

```bash
bash -x run_tests.sh              # печатать каждую команду перед выполнением
bash -n run_tests.sh              # только проверить синтаксис, не выполнять
bash -e run_tests.sh              # прервать при первой ошибке
bash -v run_tests.sh              # печатать строки скрипта по мере чтения
```

Можно включить трассировку изнутри скрипта:

```bash
#!/bin/bash
set -x    # включить
# ... код ...
set +x    # выключить
```
